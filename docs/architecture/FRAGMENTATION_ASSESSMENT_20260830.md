## 一、先確認診斷（數據，不是同意）

owner 的判斷是「每個 session 各自造一套」。這比「部件沒接起來」更準確 ——
不是缺了 B，是 **A 被重複造了 N 次**。實測支持這個判斷：

### 1.1 同一件事被幾支腳本各自實作

`scripts/checks/*.py` 共 **184 支**（扣掉 test_ 開頭為 182 支）：

| 同一件事 | 各自實作 | 今日是否因此出事 |
|---|---|---|
| **自算專案根路徑** | **110 支**（122 處） | ✅ **兩次** —— `parents[2]/"logs"` 讀到誘餌檔回 0；`route-sync-check` 三層 `Split-Path` 算到 monorepo 根 |
| 自己開 `docker exec` | 39 支 | — |
| 各自讀 `scheduler.py` | 16 支 | — |
| 各自連 DB | 11 支 | — |
| 各自讀 `cron_events` | 6 支 | ✅ 我在**同一個檔案裡**重寫了一份路徑推導，而上方 100 行就有 `_cron_events_path()` |

### 1.2 共用函式庫存在，但幾乎沒人用

`scripts/checks/lib/`：`env_loader.py`／`ts_source.py`／`__init__.py`
**實際引用它的：6 / 182 支（3.3%）**

> 這一行是整份評估的核心：**不是沒有共用層，是共用層沒有成為預設路徑。**

### 1.3 路徑深度的分歧

```
parents[1] → scripts/        3 處
parents[2] → repo 根       113 處   ← 正確
parents[3] → monorepo 根     6 處   ← 部分刻意（跨 repo 稽核）
```

重點不是誰對誰錯，是**同一個計算被寫了 122 次，而寫錯時完全沒有聲音** ——
Windows 上 `Path("/app/logs")` 會靜靜解析成 `D:\app\`，而那個目錄真的存在。

### 1.4 其餘四個維度

| 維度 | 現況 | 分散程度 |
|---|---|---|
| **事件流** | `cron_events.jsonl`／`ui-flow`／`ui-sweep`／`integration-health-*`／`fitness_*_history`／`system_notifications` 表／Prometheus／`line_digest_buffer` | **9 條**，格式與位置各異 |
| **資料庫** | 單一 PG，但 `notifications`(0 筆) 與 `system_notifications`(4,989 筆) 並存 | 有殘留表 |
| **執行腳本** | `scripts/` 下 11 個子目錄（checks/sync/health/ops/deploy/dev/init/backup/hooks/utils/archive） | 分類清楚，**但入口不統一** |
| **文件** | `docs/` 402 份 ＋ `wiki/memory/` 13 個子目錄 | 已有 402 檔進向量庫 |
| **檢核機制** | daily 約 90 步＋weekly 92 步＋PostToolUse hook＋pre-commit＋walkthrough | **5 層，各有各的產出格式** |

## 二、為什麼會這樣（機制，不是責備）

1. **每個 session 的最短路徑就是「自己寫一份」。**
   引用共用層要先知道它存在、知道它的介面；自己寫 `Path(__file__).parents[2]` 是三秒的事。
   **共用層沒有成為預設路徑，就不會被用。**

2. **重複實作的錯誤是靜默的。** 路徑算錯不會拋例外，會讀到別的檔案；
   `is_available()` 回 True 而呼叫全失敗；`text[:8000]` 對中文超標 4 倍。
   **沒有聲音 ⇒ 下一個 session 不知道前一個踩過。**

3. **既有的治理工具本身也是多部件的**（腳本＋runner 條目＋索引宣告），
   所以同一個病也長在治病的工具上。

4. **規模放大**：57 排程／92 weekly／736 API path／402 文件。
   每個 session 加一兩個部件，缺的那一半就累積。

## 三、建議（三層，依「代價／效益」排序）

### ⚠️ 先講不建議做的

**不建議「重寫 184 支腳本改用共用層」。** 理由：
* 113 支的 `parents[2]` **是對的** —— 改它們是純 churn，零效益且有風險。
* 大規模改動會產生大量 diff，把真正的變更淹沒。
* 本 repo 已有前例：範本治理鋪太廣而失血（L58／L59）。

### 建議 1（低代價、高效益）：讓共用層成為**新增時的預設路徑**

沿用本 repo 已驗證有效的 `declaration_gate` 模式 ——
**存量走基線、新增才擋**：

1. 擴充 `scripts/checks/lib/`：
   * `paths.py` —— `repo_root()`／`docs_dir()`／`logs_dir()`／`cron_events_path()`
     （後者已有實作，散在 `cron_silent_dormant_check.py` 裡，抽出來即可）
   * `db.py` —— host／容器兩種連線的單一入口（現有 11 支各寫一份）
   * `docker.py` —— `docker exec` 的統一包裝（現有 39 支各寫一份，含 `MSYS_NO_PATHCONV` 陷阱）
2. 新增一支 `check_lib_adoption_audit.py`：
   **新腳本若自己寫 `parents[N]`／`docker exec`／`create_engine` 而不走 lib ⇒ RED**；
   存量 182 支寫進基線，**基線筆數每次執行都印**（數字不動＝沒有人在清）。
3. 每次因別的原因動到某支腳本時，**順手把它從基線移除**（逐步清，不專案化）。

**預期效益**：新增的斷點歸零；存量以「動到才改」的節奏自然收斂。
**代價**：約 3 個模組 ＋ 1 支檢核。**零新增費用。**

### 建議 2（中代價）：事件流收斂為「一個入口、多個訂閱」

現況 9 條事件流各有格式，導致「查一件事要開 5 個檔」。

* **不建議**把它們合併成一張表 —— 那會動到 5 層檢核的產出契約，風險高。
* **建議**建立一個**唯讀的統一查詢入口**（`scripts/checks/lib/events.py`），
  把「最近一次 X 發生在何時／結果如何」這個問題的答案集中在一個函式裡，
  由它去讀底下那 9 條流。**改的是讀取端，不動寫入端。**

**預期效益**：新的檢核不必再自己決定去讀哪一條流（今天 6 支各自讀 cron_events 就是這個問題）。

### 建議 3（需 owner 裁示）：session 交接的「統籌點」

owner 說的「無統籌」，具體是指**沒有一個地方能回答「這個系統現在有哪些機制、各自的狀態是什麼」**。

現有最接近的是 `docs/architecture/GOVERNANCE_INTEGRATED_DASHBOARD.md`（cron 06:00 重生）。
建議把它擴充為 **session 啟動的唯一入口**，至少包含：

| 區塊 | 資料來源（皆已存在） |
|---|---|
| 排程健康 | `cron_silent_dormant_check` ＋ `producer_output_watchdog` |
| 檢核覆蓋 | weekly 步數／未納管 producer 數／基線筆數 |
| 契約鏈 | schema↔ORM↔API↔TS 的四面稽核 |
| **執行層落差** | **`CK_BUILD_COMMIT` vs `git HEAD` 差幾個 commit** ← 今天最大的斷點 |
| 待決事項 | `OPEN_ITEMS_*.md` 的未結案數 |

⚠️ 最後一列特別重要，而**我第一版對它的判斷是錯的，這裡更正**：

我原本寫「`container_image_freshness_check` 一週才跑一次，建議改 daily」。
實查後：**它早就在 daily 裡**（`run_fitness.sh:941`，帶 `--strict`），
而且**有比對 `CK_BUILD_COMMIT` vs `HEAD`**。

真正的缺口更精確：**落差時它只印一行提示，明確不計入 problems**——

```python
# 不相等**不必然是問題**（HEAD 可能已經往前走了而還沒部署），
# 所以只印出來讓人自己判斷，不計入 problems。
```

那個理由對「落後 1 個 commit」是對的，**但它沒有區分 1 個和 38 個**。
沒有門檻 ⇒ **無論落後多遠都不會紅**。
訊號存在、每天在跑、印得出來，就是永遠不會出聲。

**已修**（同日）：加入落差門檻 ——
落後 ≥20 個 commit 或 ≥24 小時 ⇒ 印「超過一天份的工作尚未部署」；
≥50 個或 ≥72 小時 ⇒ **判紅**並進晨報 digest。
用真實 commit 驗證：今早那個狀態（落後 39、距今 15 小時）⇒ YELLOW 提示；
剛部署的狀態 ⇒ 不出聲。

⚠️ 這一段本身就是本文件第 2.1 節的實例：
**我在「量了一次」之後就下了建議，而正確答案要看它的原始碼。**
