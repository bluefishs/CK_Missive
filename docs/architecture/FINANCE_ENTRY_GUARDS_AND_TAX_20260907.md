## 一、稅務資訊怎麼呈現才複核得動

### 問題不是「沒有稅額」，是「只給一個數」

原本畫面上只有含稅金額。複核一張發票要回答三件事：

| 要回答的 | 原本怎麼看 |
|---|---|
| 未稅多少 | 自己心算 ÷1.05 |
| 稅額對不對 | 沒顯示 |
| 是免稅還是漏填稅 | **看不出來** —— 稅額 0 與 5% 在畫面上長得一樣 |

第三點是真正的風險。09-06 實測有 26 張報價單稅額為 0，其中哪些是免稅、哪些是漏填，
畫面上分不出來，只能一張一張開資料庫查。

### 現在的呈現

應收帳款分頁的發票標籤，滑上去顯示四行：

```
開立日期 2026-02-25
未稅 413,333
稅額 20,667（5%）
含稅 434,000
```

稅額為 0 時，標籤直接印「免稅」兩字 —— **讓「免稅」自己說話**，而不是讓人從空白推論。

### 為什麼不做成獨立欄位

三個數字擺進表格會把欄寬吃光（那張表在 lg 容器裡已經放了 6 欄，09-06 才因為欄寬不足
把「應收未收」切掉）。複核是**逐筆**動作，hover 是對的粒度；要批次對帳的人用匯出。

## 二、同一發票對應多案件

### 原本表達不出來

`erp_invoices` 只有單一 `erp_quotation_id` 與單一 `billing_id`。一張發票跨兩個案子時，
人只能挑一個案掛上去 —— **另一個案在帳上就看不到那筆收入**，而報表不會出聲。

### 現在

新增 `erp_invoice_allocations`（發票 × 案 × 金額 × 稅額）：

* **有分攤時以分攤為準，沒有分攤時沿用發票本身的 `erp_quotation_id`** —— 既有 155 張不受影響
* 分攤合計必須等於發票金額（差 >1 元即拒絕）：一票多案時每一分錢都要落在某個案上
* 同一張發票對同一個案只能有一列（唯一鍵）：要改金額就改那一列，不要疊加
* weekly 104 新增 ⑬ 守這件事；財務健檢摘要也列它

### 為什麼不用「開多張發票」繞過

那是把系統的表達能力不足轉嫁成業務流程的負擔。客戶要的是一張發票，
我們的資料模型應該跟著業務走，不是反過來。

## 三、不開發票（互抵）

### 這是正當結算，不是缺漏

實際資料：`XLS-B114-C030-1`（18,000 已收）與 `XLS-B114-C031-1`（25,500 已收），
匯入時保留的發票欄原文就是「**不開發票**」。

原本系統沒有欄位放這件事，於是：

* 那兩筆只能寫在備註裡，稽核看不懂
* weekly 104 ⑪「已收款但沒有登錄發票」**永遠報這兩筆**
* 而永遠是紅的訊號與沒有訊號是同一個下場 —— 真的漏開發票時，沒有人會注意到多了一筆

### 現在

`erp_billings.settlement_type`：`invoice`（預設）／`offset`（互抵）／`no_invoice`（約定不開票），
外加 `settlement_note` 記依據。

* 匯入備註寫著「不開發票」的兩筆，遷移時直接轉成狀態（那是資料本來就有的事實，只是沒有欄位放）
* weekly 104 ⑪ 只算 `settlement_type='invoice'` 的 ⇒ 6 → 4
* **互抵／不開票必須填依據**（服務層擋）：沒有依據的不開票，事後無法與漏開發票分辨
* 畫面上標「互抵」或「約定不開票」，沒填依據的標橘色加驚嘆號

### 互抵的下一步（未做，需要 owner 決定）

目前 `settlement_note` 是自由文字。若要讓互抵可對帳（應收 A 與應付 B 相抵、金額必須相等），
需要 `offset_payable_id` 這類的鍵。**要不要做取決於互抵的頻率** —— 目前只有 2 筆，
為 2 筆建一套雙向對帳機制不划算；等到出現第 5 筆再說，那時也會知道實際的形狀。

## 四、把重複複核收斂掉

### 痛點不在「沒有檢核」

檢核已經有 weekly 99／104／106／107／117 與 daily 16。人工重複複核的成本在
**要人自己去七個地方看、還要自己判斷哪一條今天變了**。

### 財務健檢摘要（每日 07:00）

`app/services/erp/finance_health_digest.py`，七條「要人動手」的財務缺口：

| 條目 | 為什麼要人看 |
|---|---|
| 已收款但沒有發票（且結算方式是要開票） | 該開的票沒開，稅務風險 |
| 發票額 ≠ 請款額 | 兩邊有一邊填錯 |
| 一票多案分攤合計 ≠ 發票金額 | 有錢沒落在任何案上 |
| 互抵／不開票沒寫依據 | 事後無法與漏開分辨 |
| 應付沒有對應請款 | 「這筆應付對哪次請款」答不出來 |
| 廠商名對得到主檔卻沒填鍵 | 名稱是快照、鍵才是關聯 |
| 執行中 >365 天且 0 請款 | 可能收了沒登，也可能真的忘了 |

三個設計決定：

1. **只講變化**：與昨天的快照比對，**只推新增的**；沒有變化就安靜。
   一份每天都一樣的報表，第三天起就沒有人看了。
2. **落點是站內通知**，不是 LINE（owner 2026-09-03 明確糾正過的原則）。
3. **刻意不含**金額語意類存量（那是 weekly 104 名冊在追）與系統故障（那是 daily runner 的事）。
   一份什麼都報的摘要等於沒有摘要。

### 填報當下的守衛（weekly 117 守著它們）

事後稽核回答「資料現在乾不乾淨」，這一層回答「**下一筆填進來會不會又髒**」：

| 入口 | 擋什麼 |
|---|---|
| 應付／指派 | 名稱解析不到就出聲；併寫（`銢欣有限公司乃耳企業社`）直接擋 |
| 發票 | 稅額須 0 或 5%；金額不得超過所屬請款；未指定請款時自動綁同額且唯一的那一期 |
| 收款 | 不得超過請款額 |
| 互抵／不開票 | 必須填依據 |

weekly 117 **用執行時呼叫服務層**驗證每一條會不會擋，不用 grep —— grep 只能證明程式碼裡
有那段字，證明不了它會擋（2026-08-30 在 hook 上付過這個學費）。含 3 條負向控制。
