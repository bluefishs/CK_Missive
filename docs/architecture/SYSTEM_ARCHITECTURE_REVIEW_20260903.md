# 整體架構、流程設計與服務——覆盤與規劃（2026-09-03）

> 對象：owner。範圍：整套 CK_Missive（不只金流鏈）。承接 `RETROSPECTIVE_20260903_ERP_CHAIN.md`（那份是金流鏈的細節，這份是全景）。
> 數字是 09-03 晚量的，會過期；判斷不會那麼快過期。

## 一句話

**系統的能力已經超過使用它的人。** 114 頁、155 支端點、90 張表、63 個排程、196 支檢核；但近 30 天有操作紀錄的只有 5 個人，承辦案件最多的兩位（邱元宏 147 件執行中、洪慶忠 21 件）**沒有在系統上操作**——他們的資料是由雅慧維護總表、再由我匯入。所有「流程設計」的建議都從這個事實出發：**資料進入系統的地方，決定了流程能不能自己跑。**

## 2. 五條主流程與成熟度

| 流程 | 誰在用 | 資料怎麼進來 | 成熟度 | 主要缺口 |
|---|---|---|---|---|
| **公文＋行事曆** | 王駿穠（1,479 次／30 天）、張雅惠 | 線上登錄（2,051 件） | **高**：主力流程，日常在跑 | 附件與案件關聯靠人 |

## 3. 跨流程的結構性問題（七條）

1. **入口錯位**。業務資料的真值在總表（Excel），系統是它的下游。只要這樣，「線上報價單機制」「成案即應收」「稽催到人」都只對匯入後的存量有效，增量仍靠匯入。
2. **同一事實多份**（L138 家族）。白名單四份、排序兩處、表頭三套、防呆兩處、案號兩制。每次都是「改一處漏其餘」，靠打端點才抓到。
3. **語意沒寫死**。金額含稅／未稅、年份西元／民國、狀態中文／英文、案號舊制／新制——每一組都各自出過事，修法都是「在讀寫兩端各加一段轉換」，沒有一個地方宣告「這欄就是這個意思」。
4. **沒有起點的鏈**。標案→建案回指、成案→第一期、通知→承辦：機制都活著，缺的是第一筆資料或第一個收件人。
5. **檢核的產出沒有固定收件人**。103 支 weekly、15 支 daily，紅燈寫進歷史檔與晨報，但「誰負責這支紅燈」沒有名字（chronic_red_audit 只讓它可見）。09-02 的 CRLF 事故就是報了兩天沒人收。
6. **服務層分層是方向不是現況**。頂層散戶 52 支、直連 DB 的檔案還在；測試 mock repository 蓋不到直連段（08-28 已付過代價）。
7. **驗證的替身**（L124／L139 家族）。服務層通過≠端點通過、rollback≠沒寫入、grep 命中≠功能存在。這兩天三種都再犯一次。
