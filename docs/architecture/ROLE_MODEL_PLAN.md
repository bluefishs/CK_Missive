# 角色與帳號機制：/staff 與 /admin/user-management 的定位

> 建立：2026-08-19
> 觸發：owner「應釐清 /staff 與 /admin/user-management 定位與管理機制，
> 　　　避免後續單一帳號多重角色混淆，如加入財務（相關 ERP 或財務）或人資等角色對應網站站點」
> 　　　「如張坤樹視董事長、賴秀玲為財務……」
>
> **本文是評估與方案，不是已完成的實作。** 待決事項在 §4。

---

## 1. 現況（實測）

| 項目 | 實測值 |
|---|---|
| 在職帳號 | 12（staff 5／admin 5／superuser 1／user 1） |
| 角色種類 | **4 種**：superuser／admin／staff／user（+ unverified） |
| `role_permissions` | 5 筆，一個角色一筆 |
| 董事長 張坤樹 | `role = admin` |
| 財務 賴秀玲 | `role = admin` |
| 業務 王駿穠 | 兩個帳號（`aaronfly1978` 業務用、`jujuiacc` 管理用） |

**問題不是「權限不夠用」，是「職能無法表達」**：張坤樹是董事長、賴秀玲是財務、
王駿穠是業務，而系統裡他們全是同一個 `admin`。

### 兩個頁面現在的差別

| 頁面 | 實際行為 | 定位 |
|---|---|---|
| `/staff` | 列出**所有帳號**（不帶 canonical_only） | 人員 |
| `/admin/user-management` | 帶 `canonical_only: true`，**一人一列** | 帳號 |

兩邊呈現不同不是 bug，是**它們回答不同的問題**——但這件事沒有寫在任何地方，
所以看起來像不一致。2026-08-19 已在 `/staff` 標出「同一人」關係。

---

## 2. 核心分辨：**人 / 帳號 / 職能** 是三件事

目前系統把三者壓在同一個 `users.role` 欄位上，於是：

- 一個人有兩個帳號 → 看起來像兩個人（王駿穠）
- 一個人有兩種職能（董事長也要看財務）→ 只能都給 admin
- 「能不能進管理後台」與「能不能看財務」綁在一起 → 無法只開其中一個

| 概念 | 該回答什麼 | 現在存在哪 | 建議 |
|---|---|---|---|
| **人**（同仁） | 誰在這家公司、職稱是什麼 | `users.full_name` + `canonical_user_id` | `/staff` 管這個 |
| **帳號**（登入身分） | 用哪個信箱登入、啟用與否 | `users` 一列 | `/admin/user-management` 管這個 |
| **職能**（能做什麼） | 財務／人資／業務／管理 | **只有一個 `role` 欄位** ← 瓶頸 | 見 §3 |

---

## 3. 三個方案

### 方案 A：加「職能標籤」，不動現有 role（建議先做）

`users` 已有 `department` 與 `position` 兩個欄位（目前多半空著）。
先用它們表達職能，`role` 維持只管「系統權限層級」：

```
張坤樹  role=admin   position=董事長
賴秀玲  role=admin   position=財務
王駿穠  role=staff   position=業務    （aaronfly1978，實際業務身分）
```

- **代價幾乎為零**：欄位已存在、不動權限邏輯、隨時可退。
- 立刻解決「看不出誰是誰」的痛點（人員頁顯示職稱）。
- **不解決**「財務只能看財務模組」——那需要方案 B。

### 方案 B：角色多對多 + 模組權限（真正的 RBAC）

新增 `user_roles`（一人多角色）與 `role_module_permissions`（角色 × 模組）。

```
賴秀玲 → [財務]          → ERP 全部、公文唯讀、人資不可見
張坤樹 → [董事長, 管理]  → 全部唯讀 + 管理後台
王駿穠 → [業務]          → 報價/承攬/標案可寫、ERP 唯讀
```

- 這是「未來加入人資站點」時**必須**要有的東西：否則人資資料一開放，
  現在 5 個 admin 全部看得到。
- 代價：`require_admin` 涵蓋 **156 個端點**，改判準要逐一驗；
  且 2026-08-10 才把「管理員判定」從四份收斂成一份
  （`dependencies.is_admin_user`），**新機制必須接在那唯一實作上**，
  不能再長出第二份判準。

### 方案 C：一人一帳號（合併登入身分）

把王駿穠的兩個帳號真正合併成一個，用角色切換管理/業務視角。

- **現在不建議**：`aaronfly1978` 三天前還在用、掛著 6 個專案指派，
  而 `jujuiacc` 是每天在用的管理帳號。合併會動到 RLS 與歷史指派。
- 且 owner 已說明「王駿穠是特例」——為一個特例改動身分模型不合比例。

---

## 4. 建議路徑與待決事項

**建議：先 A，在要開人資站點之前做 B。**

理由：A 解決「看不出誰是誰」（現在就會痛），成本近乎零；
B 解決「不該看到的看得到」（**在人資資料進系統之前不會痛，之後會很痛**）。
順序不能顛倒——等資料進去了再做隔離，就得處理既有資料的可見性回溯。

### 待 owner 決定

1. **職稱怎麼填**：董事長／財務／業務／人資……這份清單由 owner 定，
   我不從現有資料猜（猜錯會變成寫在每個人資料上的錯誤標籤）。
2. **角色是否要多重**：賴秀玲若同時管財務與人資，方案 A 的單一 `position`
   就不夠 → 直接進 B。
3. **人資站點的時程**：這決定 B 要多早做。
4. **`/staff` 與 `/admin/user-management` 是否合併**：兩者現在確實有重疊。
   建議**不合併**，但把定位寫在頁面上（「人員」vs「登入帳號」），
   讓使用者一眼看出差別 —— 而不是靠猜。

## 5. 已完成（2026-08-19）

- `/staff` 標出「同一人」關係：同仁有兩個登入帳號時，在姓名旁標記並說明
  兩者是同一人、資料可見範圍涵蓋兩個帳號。
- 標籤刻意用「同一人」而非「分身」：owner 指出被標成 alias 的
  `aaronfly1978` 才是**實際業務身分**，而 canonical 的 `jujuiacc` 是管理帳號
  —— 「分身」暗示的主次方向與事實相反。

⚠️ **連帶影響需要注意**：報價單的「服務人員／E-mail」取的是 **canonical**
（ADR-0025：分身不得顯示成另一個人），所以王駿穠的案子會印出
`jujuiacc@gmail.com`（管理帳號）而非 `aaronfly1978@gmail.com`（業務身分）。
這在正式對外文件上是錯的窗口資訊。修法取決於 §4 的決定，本輪未動。
