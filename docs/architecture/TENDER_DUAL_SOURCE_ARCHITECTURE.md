# 標案雙來源架構：PCC 與 ezbid 如何對應與互補

> 建立：2026-08-26
> 觸發：owner「兩個標案資料來源到底如何對應與互補，請釐清架構與服務，
> 　　　如前述常無法連結等相關問題紀錄」
> 前置：owner「原則上 PCC 為主要來源，不太可能會無案件資料」
>
> **這一份回答三個問題**：兩個來源各給什麼／它們靠什麼對應／為什麼常常對不上。
> 所有數字都是 2026-08-26 實測，不是估計。

---

## 1. 兩個來源各是什麼

| | **PCC**（政府電子採購網） | **ezbid** |
|---|---|---|
| 定位 | **權威來源**。owner：「不太可能會無案件資料」 | 第三方彙整站 |
| 存量 | **66,341** | 49,497 |
| 抓取 | `pcc_today_scraper` 每 2 小時 | `ezbid_scraper` 每小時 |
| 主鍵 | `unit_id` = base64 的 `pkPmsMain`（`NzEzMDE4NDg=`）＋ `job_number` | `ezbid_id` |
| **`budget` 覆蓋** | **4 筆**（0.006%） | **48,841 筆（98.7%）** |

**⇒ 這一行就是互補的全部理由**：權威來源有廣度與正確性，**但沒有預算金額**；
ezbid 存量少一些，**卻幾乎每一筆都有預算**。

> ⚠️ PCC 沒有 budget **不是抓取失敗**：預算金額寫在 PCC 的**詳情頁本文**，
> 列表頁不給。08-19 已為此加了「沒有金額才去抓詳情頁」的即時補抓
> （`tender_module/search.py`），但那是**單筆、使用者點進去時才觸發**，
> 不會回填整個庫。

## 2. 三組識別碼，而它們的語意不一致

這是「常無法連結」的**第一層**原因 —— 同一個欄位名，在兩個來源是兩種東西。

| 欄位 | `source='pcc'` | `source='ezbid'` |
|---|---|---|
| `unit_id` | base64 `pkPmsMain`（`NzEzMDE4NDg=`）**65,976 筆** | **點分機關代碼**（`3.13.31.90`） |
| `ezbid_id` | （空） | 兩種格式並存 → 見下 |
| `job_number` | 標案案號 | 標案案號（**兩邊同一個語意，唯一可靠的共同鍵**） |

### 2.1 `unit_id` 的兩種語意，已經咬過一次

`detail_enrichment.py` 假設 `unit_id` 是 PCC 的 `pkPmsMain`，於是對 ezbid 的
`3.5.10.100` 去 PCC 詳情頁查 org_id ⇒ **查不到、每筆 error**。
2026-08-26 實測 `org_ok=0 / errors=2`，而同一支函式手動餵 base64 **成功**。

修法：點分格式就直接當 org_id 用（ezbid 的 `unit_id` **本身就是** openfun 要的
org_id），不必再打 PCC —— 順帶省掉 ezbid 那一段的外部請求。

### 2.2 `ezbid_id` 的兩種格式，來自站台改版

| 格式 | 筆數 | 說明 |
|---|---|---|
| 純數字（`123456`） | **37,980** | 2026-08-02 站台改版**前**的 tender id |
| `{機關代碼}/{案號}`（`A.21.100.36/TH115144`） | **11,470** | 改版**後**的複合鍵 |

前端路由 `/tender/ezbid/:ezbidId` 對含斜線的那一種靠
`encodeURIComponent`（`%2F`）通過 —— **系統自己產生的連結沒問題**，
但人手輸入或舊書籤只給機關代碼（`A.47.3`）時會查無，而畫面
原本只說「查無此標案」⇒ 已改為明說「這個編號不完整」（見 §5）。

## 3. 為什麼常常連不上：門檻結構上永遠達不到

ADR-0046 的自動 link 用 **`pg_trgm` 相似度計分、HIGH 門檻 0.85**。

**而 `pg_trgm` 對中文無效** —— 08-19 實測兩筆標題與機關名**完全相同**、
`similarity` 都是 **0.0000**。這不是門檻調得太嚴，是**分數永遠到不了**。

實測現況：

```
已配對（pcc_match_unit_id 非空）   2,204 筆  ＝ ezbid 的 4.5%
```

### 3.1 改用精確鍵可以配到多少

以 **`job_number` ＋ 標題前 20 字**（兩者都相同才算）配對：

```
同 job_number 的組合          96,991 組
  ├ 標題前 20 字也相同         17,843 組  ← 可靠
  └ 標題不同                   79,148 組  ← 撞號，必須排除
可靠配對涉及  ezbid 10,912 筆 / pcc 17,839 筆
```

⚠️ **只用 `job_number` 會錯得很嚴重**：79,148 組是撞號（不同機關用同一個
案號編制），佔 81.6%。08-19 也記過「1,129 組同號不同標題」。
反過來**只用標題**也不行：`B115076 公開招標` 與 `B115077 公開取得報價單`
是**兩個不同的案子**，標題卻一樣。**兩個條件缺一不可。**

### 3.2 配上之後實際換到什麼

```
可靠配對 17,843 組中，「ezbid 有 budget 而 pcc 沒有」＝ 17,610 組（98.7%）
```

**⇒ PCC 有 17,839 筆可以從 ezbid 補到預算金額，而現況只補到 12%。**
這是零成本的（純資料庫運算，不打任何外部站台）。

## 4. 服務層：誰負責哪一段

```
                 ┌─ pcc_today_scraper ──┐
   外部抓取       │  每 2 小時            │──→ cache.save_tender_records()
                 └─ ezbid_scraper ──────┘         │  寫 tender_records
                    每小時                         └→ 寫 tender_company_links
                                                      （得標/投標廠商）
   跨來源配對     enrichment.enrich_all_unmatched()   ← ADR-0046，pg_trgm，4.5%
                  ⚠️ 中文無效，見 §3

   詳情補料       detail_enrichment.enrich_recent()   ← 每日 03:45（2026-08-26 才接上）
                  org_id → openfun API → 採購性質/底價/決標/廠商

   即時查詢       tender/search.py                    ← DB-first，缺 budget 才抓 PCC 詳情頁
```

| # | 議題 | 為什麼需要決定 |
|---|---|---|
| T1 | **要不要用精確鍵重跑一次全庫配對**（2,204 → 可達 17,843） | 純資料庫運算、零外部請求、可 dry-run 先看。但它會改寫 `pcc_match_*` 三個欄位共 ~15,600 筆，屬於批次寫入業務資料 ⇒ **不擅自執行** |
| T2 | ADR-0046 的 `pg_trgm` 判準要不要**廢止** | 它結構上永遠達不到門檻（中文 similarity 恆 0）。留著它等於留一個永遠不會成功的機制，而它每天都在跑 |
| T3 | 決標金額 | 實測 openfun **有**決標結構（決標日期、得標廠商、決標方式），但**總決標金額視機關是否公開** —— 抽測那筆有 `決標資料:總決標金額是否公開` 而**沒有金額欄位**。⇒ `award_amount` 不會是 100%，那是資料本身的性質不是缺陷 |

## 7. 判準（這一輪確立的）

1. **同一個欄位名在兩個來源可能是兩種東西** —— `unit_id` 已經咬過一次，
   而失敗方式是「每筆 error」而不是「報錯說語意不對」。
2. **配對鍵不能只用一個** —— 只用 `job_number` 有 81.6% 是撞號，
   只用標題會把兩個不同招標方式的案子併成一筆。
3. **中文不要用 `pg_trgm`** —— 它不會報錯，它回 0.0000。
4. **「查無」與「編號不完整」是意思相反的兩件事**，不該共用一個畫面
   （同 08-20「空清單退化成數字」、同日 StaffPage「空表格 vs 載不到」——
   本 repo 第三次遇到同一個形狀）。
