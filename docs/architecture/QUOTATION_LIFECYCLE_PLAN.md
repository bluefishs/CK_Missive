## 1. 回簽流程

### 1.1 缺的是「附件是什麼」，不是「能不能上傳」

`pm_case_attachments` 沒有分類欄位，所以「系統產生的報價單」「客戶回簽的報價單」
「其他佐證」三者在資料上長得一模一樣，只能靠檔名猜 —— 而靠檔名比對正是本專案
反覆踩過的那一類（檔名一改，判定就靜靜失效）。

**方案：加 `doc_type` 欄位**（`generated_quotation` / `signed_quotation` / `other`）。

- 既有 N 筆一律填 `other`，**不猜**。「不知道它是什麼」與「它是其他」在資料上
  必須分得出來 → 用 `NULL` 表示未分類，`other` 表示人工判定過。
- 系統輸出的報價單自動標 `generated_quotation`（已實作的 `archive()` 直接帶上）。

### 1.2 狀態機：只加不改

現有 75 筆 `confirmed` 代表「已成案」，**不得重新定義它的語意** ——
那 75 筆是歷史事實，改它等於竄改紀錄。

建議新增兩態，插在中間：

```
draft ──→ issued ──→ signed ──→ confirmed
草稿      已出單      客戶已回簽    已成案（現有語意不動）
          ↑產生正式   ↑上傳回簽檔
           文件時      並按確認
```

- `issued`：呼叫 export-document 成功時自動轉（**只從 draft 轉**，不回頭改已成案的）
- `signed`：上傳 `doc_type=signed_quotation` 的附件並按「確認回簽」時轉
- `confirmed`：維持現行成案流程

⚠️ **既有 88 件承攬案件全部沒有回簽檔**。新流程若要求「必須有回簽才能成案」，
會讓歷史案件全部變成不合規 —— 所以**強制只對新案件生效**，既有案件標為
「歷史案件（無回簽紀錄）」而不是「缺件」。兩者意思不同：前者是事實，後者是待辦。

## 2. 帳號對應機制（避免頁面混雜不同使用者的填報紀錄）

### 2.1 先講一個已經修掉的前提

**77 張報價單的 `created_by` 全部是 NULL** —— 不是欄位不存在，是端點建立時
沒有把使用者傳進去（`service.create` 第 151 行早就在寫 `created_by`，端點卻沒傳）。
2026-08-19 已修（連同 Excel 匯入與 PM 案件建立，掃出同型共 3 處）。

**在此之前，系統無法回答「這張報價單是誰開的」** —— 所以「帳號對應」的第一步
不是做過濾，是先讓資料有人。

### 2.2 三種可見性策略

| 策略 | 說明 | 代價 |
|---|---|---|
| **A. 只做「我的」篩選鈕**（建議先做） | 資料照舊全看得到，列表加一個「只看我建立的」切換 + 顯示建立者欄位 | 幾乎為零。不改權限、不改既有查詢、隨時可退 |
| B. 預設只看自己、可切換全部 | 進頁面預設過濾 `created_by = 我` | 中。**77 張舊資料 created_by 是 NULL，預設過濾後會全部消失** ⇒ 必須先回填或加 NULL 例外 |
| C. RLS 強制隔離 | 看不到別人的報價單 | 高，且與現況不符 —— 報價/承攬本來就是要互相支援的業務，硬隔離會擋住正常協作 |

**建議 A**：owner 的痛點是「頁面混雜」＝**看不出哪筆是自己的**，而不是「不該看到別人的」。
A 直接解決那個痛點，且不動任何權限語意。若之後發現真的需要隔離，再從 A 走到 B。

⚠️ 若選 B，必須先決定 **77 張 NULL 的歸屬** —— 憑空指定一個人是造假；
可行的作法是留 NULL 並在 UI 標「未記錄建立者（2026-08-19 前）」。

## 3. 既有案件補件

### 3.1 不需要新入口

承攬案件詳情頁 → 附件分頁 → 上傳，選 `doc_type = 客戶回簽報價單`。
既有 88 件全部走同一條路，不做「批次補件」特別頁 ——
補件是逐案判斷的事（要找出那份紙本掃描檔），批次介面幫不上忙。

### 3.2 分批建議

| 批次 | 件數 | 理由 |
|---|---|---|
| 優先 | **執行中 13 件** | 案子還在跑，回簽件現在找得到，且之後對帳會用到 |
| 次之 | 已結案 **75 件** | 屬歷史歸檔；找不到就標「無回簽紀錄」，**不要留空**（空白會被讀成還沒補） |

### 3.3 進度看得見

補件是一件會拖很久的事，所以要有一個地方回答「還剩幾件」：
承攬案件列表加一欄「回簽」（✓／—／未標記），三態分明。
**刻意不做提醒推播** —— 歷史補件沒有時效壓力，每天推一則只會被略過
（本專案已有「告警疲勞讓真的紅燈沒人信」的紀錄）。
