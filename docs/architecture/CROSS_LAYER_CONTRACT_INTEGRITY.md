## 家族一：Pydantic 靜默丟棄（#2 #3 #4）

Pydantic 預設 `extra='ignore'` —— **送來的欄位若 schema 沒有，直接丟掉，不報錯。**

實測：`backend/app/schemas/erp/` 底下 **`extra=` 出現 0 次**，
也就是全部走預設。於是這件事必然反覆發生：

```
前端送 payment_amount=2249163 ──→ ERPBillingCreate 沒有這一欄
                                    ↓
                              Pydantic 丟掉，不吭聲
                                    ↓
                        DB 存下「已收款、金額 null」
                                    ↓
                        統計卡顯示「已收 0」，看起來像還沒收
```

**三層都沒有人會報錯**：前端以為送了、後端以為沒收到、資料庫存了一個矛盾狀態。

### 為什麼測試抓不到

- 後端單元測試**直接建構 schema 物件**，不會經過「前端送什麼」那一步
- 前端測試 mock 掉 API，不會知道欄位被丟了
- OpenAPI 契約測試比對的是**已宣告的欄位**，不會問「有沒有欄位漏宣告」

### ⚠️ 2026-08-18 後記：這個根治本身造成了一次線上故障

開了 `forbid` 之後，**編輯任何一筆應收／應付都 422**。

根因：應收/應付填報頁的 Create 與 Update **共用同一個 payload 物件**，
而 `erp_quotation_id` 只在 Create schema 裡有。原本它被靜默丟棄，
開 forbid 之後變成 422。

我開之前有掃前端 payload，掃出「0 個欄位缺失」——
**那次掃描用「欄位交集最大」去猜 payload 對應哪個 schema，
而共用 payload 的交集最大者永遠是 Create（欄位比較多）**，
於是 Update 缺的欄位完全沒有被看見。

> **掃描找錯了比對對象，就等於沒掃。**
> 而它還會回一個「✅ 未發現問題」，比不掃更糟。

修法三層：
1. `erp_quotation_id` 改為**只在建立時送**（語意上也對：帳款不能改掛到別張報價）
2. 寫法要說出規則 —— payload 本體不含它、建立時才補。
   第一版是在 `mutate` 前解構掉，行為正確但**字面值裡仍看得到那一欄**，
   讀程式碼的人與檢核都會以為更新時會送。
3. `write_payload_schema_audit`（weekly 62）以**端點常數為錨**比對，不用猜

### 寫這支檢核時我自己踩的兩個坑（都被負向測試抓到）

- **第一次負向測試無效**：我還原的是 `mutate` 那一行，而 payload 字面值
  兩版相同 —— 測了一個不會改變輸入的東西。
- **正則裡有一個退格字元**：heredoc 裡寫 `payload\b`（想表達詞界），
  非 raw 字串把它變成 `\x08`，正則永遠不匹配 → 抓到 0 個 payload → **印 GREEN**。
  一支找不到東西就回綠的檢核，比沒有檢核更糟。

  往後含反斜線的內容一律用 Write/Edit 工具產生，不走 heredoc。

### 根治：寫入端 schema 一律 `extra='forbid'`

```python
class ERPBillingCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")
```

前端送了 schema 沒有的欄位 → **立刻 422 並指名是哪一欄**，而不是靜默丟棄。

**只加在 Create/Update（寫入端）**：
- 讀取端（Response）加 `forbid` 沒有意義（是我們自己組的）
- Query/Request 參數類加了會擋掉合法的擴充（例如前端多送一個 `_t` 破快取）

⚠️ **這是行為變更**：原本被默默丟棄的欄位現在會 422。
所以必須先掃「前端實際在送什麼」，把合法欄位補進 schema，
**再**開 forbid —— 順序反了會讓正在用的功能壞掉。

## 家族二：顯示層寫死了應該來自資料的東西（#5 #6）

```tsx
counterparty: '委託單位',              // 欄位標題被當成值
{ title: '發票號碼', dataIndex: 'description' }  // 一欄裝三種語意
```

共同形狀：**開發時「先放一個看起來對的東西」，然後它就留在那裡了。**
不會報錯，畫面也是滿的 —— 只有懂業務的人打開才看得出不對。

這一類**靜態檢查抓不到**（字串是合法的），
唯一的偵測器是「人打開頁面覺得不對」——
所以它們往往由 owner 回報，而不是由 159 支檢核發現。
（本專案 08-13 已量化過這件事：人提問 6 : 檢核 0。）

**能做的**：`ExpensesTab` 那種「一欄多語意」加 `type` 欄標明每列是什麼；
硬編值改為 props 傳入並在缺值時顯示「（未設定）」而不是假值。
**不能做的**：期待檢核抓到它們。

## 業務規則：標案類不應有報價明細

owner 2026-08-17：「若是標案應無報價明細」＋
「報價可明列作業單價統計成本，而標案涉及多項程序不易填列成本」。

`category` 01=委辦招標（標案）／02=承攬報價：

| 對象 | 報價明細 | 估列成本 |
|---|---|---|
| `02` 承攬報價 | ✅ 逐項單價 | ✅ 要求 |
| `01` 委辦招標 | ❌ **不呈現** | ❌ 不列入缺口 |

已落實於生命跡象與填報缺口（`p.category = '02'`），
**報價明細分頁也應依此隱藏** —— 對標案類顯示一個填不了的分頁，
就是在要求對方做不可能的事（同「要求標案填成本」那個錯）。
