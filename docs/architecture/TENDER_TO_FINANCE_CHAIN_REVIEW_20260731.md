### ⛔ B. 識別斷 — 建案防重複對 ezbid 完全失效

`graph_case.py` 的防呆是：

```python
if req.job_number and req.job_number.strip():
    existing = ... PMCase.notes.ilike(f"%{req.job_number}%")
```

ezbid 沒有 job_number → **條件不成立 → 完全跳過查重 → 每按一次就多一個案件**。

更關鍵：標案 `2227632` 的 `title` 與承攬案件 `187` 的 `project_name`
**是同一個字串**（「桃園市公共設施用地設施物調查測量及工程開闢分析規劃第二期」），
但系統沒有任何機制看得出它們是同一案——查重只認 job_number，不認案名/機關。

> 未量測：全庫「標案標題 == 承攬案件名稱」的重疊筆數（查詢被中止，未取得數字）。
> 至少 1 例已由 owner 實際踩到。

### ⛔ C. 中途插入 — 直接建立的承攬案件沒有上游

| 欄位 | 案件 187 實際值 |
|---|---|
| `project_code` | `CK2026_01_01_006` |
| `case_code` | **NULL** |

## 3. 完善方案（分層，附成本與風險）

| 層 | 內容 | 成本 | 風險 | 需 owner 決策 |
|---|---|---|---|---|
| **L1 入口** | `job_number` 改選填；ezbid 以 `ezbid_id` 為識別；ezbid 分支加「一鍵建案」 | 小（2 檔） | 低 | 否 |
| **L2 識別 SSOT** | 建案前以「案名 + 招標機關」比對既有 `PMCase` / `ContractProject`；命中則回傳既有案件並提供「**關聯到既有案件**」而非新建 | 中 | **中**：比對策略錯會誤擋 | ✅ 是 |
| **L3 回指** | `tender_records` ↔ 案件雙向連結（案件顯示來源標案、標案顯示已建案件） | 中（需一個關聯欄位或表） | 低 | ✅ 是（是否允許一案多標） |
| **L4 財務接續** | 從承攬案件建立報價時，若有來源標案 → 預填預算/機關/案名（現在只帶 `project_code` + 案名） | 小 | 低 | 否 |
| **L5 呈現一致性** | 兩個 ExpensesTab **不強行合併**（一個是唯讀彙總、一個是 CRUD，語意不同＝過度抽象風險），改以 regression 鎖住「都必須可鑽取」 | 已完成 | — | 否 |

### L2 需要你決定的是比對策略

1. **嚴格**：案名完全相同才視為同一案 → 漏抓多（案名常有「第二期」「(開口契約)」等差異）
2. **寬鬆**：案名相似度 + 同機關 → 抓得多但可能誤擋，需人工確認 UI
3. **不自動判定**：建案前列出「可能相關的既有案件」讓人選 → 最安全，但多一步

> 我的建議是 **3**：不替使用者判定，只把候選攤開來讓人選「新建」或「關聯既有」。
> 理由與本專案既有紀律一致——**驗證優先於收斂**，自動判定錯了比多按一次貴。

## 5. 最佳策略建議（owner 提問：就此議題提最佳策略）

### 問題的本質

號碼體系是**流程的產物**，但實務上案件經常「從中途進來」：

```
正規流程：標案 →(建案) case_code →(成案) project_code → 報價 → 核銷
案件 187：            ✗            直接建立 project_code    ✗      ✗
```

於是號碼缺一段，下游（財務）就接不上。**過去的處理方式是每次補一個 fallback**
（07-29 補 `project_code` fallback、07-31 補 `case_code`），fallback 越疊越多，
但「中途進來的案件會缺號」這個成因始終沒有被處理。

### 三個層次的對策（附成本與建議）

| 方案 | 內容 | 成本 | 效果 | 建議 |
|---|---|---|---|---|
| **A. 批次補齊**（短期） | 用同一支腳本補 188/190/191 的號與 draft 報價 | 極小 | 立即，但**治標** | 建議做，但要 owner 確認金額來源 |
| **B. 成案即自動創財務號**（中期，**最高 CP**） | `contract_projects` 建立時若無 `case_code` → 自動產號 + 建 draft 報價 | 小（單一 service hook） | **從此不再產生新的缺號案件**，fitness step 74 恆為 0 | ⭐ 首選 |
| **C. 收斂為單一案件識別碼**（長期） | 以 `case_code` 為唯一主鍵，`project_code` 降為「對外文號」屬性，移除三處 fallback | 大（需資料遷移 + 全模組改） | 根治複雜度來源 | 現階段**不建議**，待 B 穩定後再評估 |

**建議路徑：先 B、再 A、C 暫不做。**
B 是唯一會讓問題「不再新增」的一招；A 只是把既有 3 筆補完；
C 雖是治本，但要動 87 筆承攬案件 + 71 筆報價 + 三個模組的關聯鍵，
在沒有 B 先止血的情況下做 C，只是把風險放大（對照 L53 過度工程教訓）。

### 順帶指出的既有分歧（不建議現在動）

我為 187 產生的 `case_code` 是 **`CK2026_FN_01_001`**（ERP 產生器，`FN` 前綴），
而該案的 `project_code` 是 `CK2026_01_01_006`（承攬體系）。
**兩套命名規則並存**是既有現象，不是本次造成；但它會讓「同一案兩個號長得完全不像」，
人工核對時容易誤判。若採方案 B，建議一併統一產號規則 —— 這是 B 的自然附帶收益。

## 5.5 「無一鍵建案」的實際原因（2026-07-31 複查）

owner 回報 ezbid 頁看不到按鈕。逐層查證結果 —— **程式碼與部署都是對的**：

| 檢查 | 結果 |
|---|---|
| 後端 `/api/tender/detail` | `kind=ezbid`、`tender_id=8526` ✅ |
| 原始碼位置 | 按鈕在 ezbid 分支內、**不在** `pcc_match` 條件內、無條件顯示 ✅ |
| 部署產物 | `TenderDetailPage-BkJ716jk.js` 含 **2 處**「一鍵建案」+ `startCreateCase` ✅ |
| 公網供應 | 該 chunk HTTP 200；`index.html` 為 `no-store`，已指向新 `main-C02V_HSN.js` ✅ |
| 舊 chunk | `main-C25f0b1z.js` → **404**（已被新版取代） |

→ 結論：**瀏覽器分頁仍在跑部署前載入的舊 bundle**（SPA 未重新載入頁面就不會換 chunk）。
重新整理即可；若仍無，請看 DevTools → Network 的 `main-*.js` 檔名是否為 `C02V_HSN`。
